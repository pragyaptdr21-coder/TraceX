===========================================================
TraceX Phase 3 - Algorithm Specification & PDF Mapping
===========================================================

1. DETECTION OBJECTIVE
The objective is to identify multi-tier money laundering patterns in a 2 million record financial dataset and flag accounts on a 0-100 Mule Risk Index, minimizing false positives while preparing for the Blind Victim Query Test.

2. PDF-DEFINED SIGNALS & EXACT THRESHOLDS
The problem statement explicitly defines the following patterns and strict numeric thresholds:

A. High-Velocity Pass-Through
- Requirement: Flag nodes where >= 90% of incoming funds are dispersed within 3 to 15 minutes across multiple outgoing transfers.
- Thresholds: 
  - Ratio: (Total Outgoing in window) / (Incoming Amount) >= 0.90
  - Window Start: 3 minutes after incoming transfer
  - Window End: 15 minutes after incoming transfer
  - Outgoing Transfers: > 1

B. Collector Mules (L1)
- Requirement: High in-degree centrality, multiple distinct senders depositing money into a single node.
- Thresholds: No strict numeric threshold is provided by the PDF.
- Engineering Choice: We will set a configurable threshold (e.g., unique_senders >= 5) to represent "multiple distinct senders" and high concentration, avoiding false positives for standard businesses.

C. Distributor Mules (L2)
- Requirement: High out-degree centrality, slicing incoming funds into 3-7 downstream accounts.
- Thresholds:
  - Downstream Accounts: Between 3 and 7 (inclusive).

D. Cyclical Smurfing
- Requirement: Detect cyclical smurfing patterns (A -> B -> C -> A).
- Thresholds: No strict cycle length provided.
- Engineering Choice: We will detect cycles of length 2 to 4 to cover standard obfuscation loops without exponential graph traversal costs.

E. Terminal Cash-Out Identifiers (L3)
- Requirement: Outward transfers to payment wallets, P2P crypto narrations, foreign IP headers (185.x.x.x, 194.x.x.x), and headless script user-agents (Web_Emulator, Linux_Script).
- Exact Indicators:
  - IP Address: Starts with "185." or "194."
  - Device_Type: "Web_Emulator" or "Linux_Script"
  - Narration: Matches "wallet", "crypto", "p2p" (case-insensitive)

F. Graph Multi-Hop Trace
- Requirement: Trace downstream money trail up to 4 hops deep within < 2 seconds.
- Thresholds: Max Depth = 4. Latency < 2.0s.

3. ALGORITHM CHECKLIST & EVIDENCE
- [ ] Velocity Detector: Windowed self-join or aggregate on timestamps per account. Evidence includes incoming TX, outgoing TXs, ratio, and time elapsed.
- [ ] Collector Detector: Group by receiver, count distinct senders. Evidence includes sender count, incoming volume.
- [ ] Distributor Detector: Group by sender, count distinct receivers. Filter between 3 and 7. Evidence includes recipient count, outgoing volume.
- [ ] Cycle Detector: Bounded depth-first search (DFS) or 3-4 hop self-join in DuckDB. Evidence includes the accounts in the cycle.
- [ ] Terminal Detector: Simple regex/string matching on Narration, IP, and Device_Type. Evidence includes the triggering TX and the matched indicator.
- [ ] 4-Hop Traversal: Breadth-first search (BFS) starting from a victim node, up to depth 4, maintaining visited sets to prevent infinite loops.

4. MULE RISK INDEX FORMULA (0-100)
Since the PDF does not assign exact weights to the 0-100 scale, the following engineering choice is applied:
- Collector Pattern (L1) = +25
- Distributor Pattern (L2) = +25
- High-Velocity Pass-Through = +25
- Cyclical Smurfing = +25
- Terminal Cash-Out (L3) = +50 (Terminal indicators are strong evidence of mule activity)
Max score capped at 100. Each score is directly mapped to the evidence generated by the respective detector.

5. COMPLEXITY & FALSE-POSITIVE CONTROLS
- All algorithms except 4-hop and cycles will be implemented using DuckDB's vectorized SQL execution to handle 2 million rows efficiently.
- False positives are controlled by combining temporal constraints (3-15 min) and distinct counterparty thresholds (3-7 for L2, >5 for L1).
- 4-Hop traversal will maintain a `visited_transactions` set to avoid infinite loops and repeated expansions, ensuring the <2s latency target.
