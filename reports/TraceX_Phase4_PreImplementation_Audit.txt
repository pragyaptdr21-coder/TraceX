-----------------------------------------
From Problem Statement.pdf:

5. DATABASE AUDIT (DuckDB)
-----------------------------------------
Location: storage/tracex.duckdb
Table: transactions
Columns:
- internal_id (UINTEGER)
- Transaction_ID (VARCHAR)
- Sender_Account (VARCHAR)
- Receiver_Account (VARCHAR)
- Sender_IFSC (VARCHAR)
- Receiver_IFSC (VARCHAR)
- Amount (DOUBLE)
- Timestamp (TIMESTAMP)
- Payment_Mode (VARCHAR)
- Narration (VARCHAR)
- IP_Address (VARCHAR)
- Device_Type (VARCHAR)

The frontend can safely retrieve Sender, Receiver, Amount, Timestamp, Transaction_ID, Payment_Mode, Narration, IP, Device, and IFSC.

6. DETECTION OUTPUT AUDIT
-----------------------------------------
The detectors (Velocity, Collector, Distributor, Terminal, Cycle) output a List of Dictionaries.
Important fields: account_id, detection_type, score_contribution, evidence (dict).
Evidence contains transaction IDs, amounts, and timestamps.
Can frontend consume directly?: No API exists yet to serve this JSON to the frontend.

7. 4-HOP GRAPH AUDIT (trail_engine.py)
-----------------------------------------
Input: victim_account (str), max_hops (int=4)
Output: Dictionary with root_account, nodes (list), edges (list), total_hops.
Node structure: {"id": "ACC1", "layer": 0}
Edge structure: {"source": "S", "target": "R", "transaction_id": "T", "amount": 100, "timestamp": "...", "hop": 1}
Cycles handled: Yes, via visited_accounts set.
Duplicate nodes: Handled.
Layer limit: Truncated at 2000 nodes per hop to prevent explosion.
Suitable for visualization: Yes, nodes/edges format is standard for graph libraries.
