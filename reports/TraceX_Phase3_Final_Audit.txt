1. PDF REQUIREMENT MAPPING
Requirement: High-Velocity Pass-Through
-> Implementation: VelocityDetector aggregates incoming/outgoing within 3-15m bounds.
-> Exact Threshold: >= 90% incoming funds dispersed across > 1 outgoing transfer in 3-15 min window.
-> Evidence Produced: Incoming/outgoing TXs, amounts, elapsed ratios.
-> Status: Verified & Compliant.

Requirement: Collector Mules (L1)
-> Implementation: CollectorDetector distinct incoming senders constraint.
-> Exact Threshold: Not defined by PDF. 
-> TraceX Engineering Choice: >= 5 unique senders to filter ecommerce noise.
-> Evidence Produced: Sample distinct senders, counts, volume.
-> Status: Verified & Compliant.

Requirement: Distributor Mules (L2)
-> Implementation: DistributorDetector distinct outgoing receivers constraint.
-> Exact Threshold: 3 to 7 downstream accounts (PDF-defined).
-> Evidence Produced: Source account, distinct receivers list, tx volume.
-> Status: Verified & Compliant.

Requirement: Cyclical Smurfing
-> Implementation: CycleDetector depth-limited self joins.
-> Exact Threshold: Not strictly defined. 
-> TraceX Engineering Choice: 3-hop limit (A->B->C->A) for optimal 2M scale memory footprint.
-> Evidence Produced: Full cycle account trace, exact TXIDs and Amounts in the loop.
-> Status: Verified & Compliant.

Requirement: Terminal Cash-Out (L3)
-> Implementation: TerminalDetector text/substring matching.
-> Exact Threshold: IPs starting 185.* or 194.*, Device_Types 'Web_Emulator' or 'Linux_Script', and Narration crypto/p2p matches.
-> Evidence Produced: Offending indicator, the specific TX, exact matched text.
-> Status: Verified & Compliant.

Requirement: 4-Hop Graph Trace
-> Implementation: BFS queue using DuckDB chunked queries, protecting against cycles using a `visited` accounts set.
-> Exact Threshold: Hop limit = 4. Execution < 2 seconds.
-> Evidence Produced: Nodes, Layer topology, Edges (TXs).
-> Status: Verified & Compliant.

2. ALGORITHM SUMMARY
The backend utilizes vectorized data processing (DuckDB SQL) rather than single-threaded Python iteration. Aggregations, windowing, string matching, and short graph structures are directly computed natively on disk/memory chunks preventing OOM. 4-hop traces use Python to orchestrate BFS against DuckDB.

10. BLIND VICTIM READINESS
The `TrailEngine` class accepts any string `account_id` as input, querying the central `.duckdb` dynamically in real-time. It is highly robust, decoupled from hardcoded scenarios, and completely ready to process arbitrary JSON inputs/APIs.

11. PRECISION/RECALL STATUS
PENDING - Official ground truth (the 1,500 labeled mule IDs) is not currently available within the 2M CSV. The `RiskEngine` architecture operates deterministically and provides boolean presence mapping to instantly feed into sklearn metric functions upon judge evaluation.

12. FALSE-POSITIVE CONSIDERATIONS
Terminal indicators do not guarantee criminality (someone might legitimately use a Web_Emulator). We enforce multi-signal indexing rather than boolean locking. Velocity passes are deeply restricted temporally to avoid catching genuine large-business disbursements that happen over multiple days.
